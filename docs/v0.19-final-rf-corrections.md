## RF-01 — Scalar identifier comparison, original representation preserved

`workerResponse` used `cellfun(@(r)r.id==previous{j}.id,records)`. With two valid
char row IDs, MATLAB compares characters rather than scalar identifiers. Equal
length returns a logical vector; unequal lengths can fail dimension checks.
The cellfun scalar-output contract then fails, interrupting Packaging.

The comparison now uses `string(r.id)==string(previous{j}.id)`. The same
comparison-only normalization covers request parent lookup and the Packaging/
adoption lookup in `perform`. No ID, identity, snapshot, source record or MAT
representation is rewritten. Equality is exact and case-sensitive; it does not
trim text, accept prefixes, or collapse different IDs. Canonical validation of
the original records remains required, including exact identity representation.

## RF-02 — Explicit response protocol before atomic acceptance

`Controller.accept` previously entered policy handling only if `ledgerPolicy`
existed. Removing it bypassed APPEND merge and let the delta replace the complete
project. The new boundary requires the full closed response envelope:
operationId, epoch, action, project, value, compatibility, elapsed_s, ledgerPolicy.
Metadata must be scalar/finite where appropriate; policy and action must be known.
The operation/action/epoch must match the pending immutable operation, and the
policy must match the policy derived from that operation, not a worker fallback.

- APPEND validates the returned project/history shape and correspondence of
  actual result values to unique exact delta records, then uses the unchanged
  canonical history merger to validate both inputs and form the union.
- REPLACE is allowed only for NEW/DEMO/LOAD. Its complete project is canonically
  validated, compatibility checked, and NEW must return the requested project ID.
  Its value cannot carry an unrelated result payload. Empty compatibility vectors
  compare independent of0x0/0x1 orientation, then use canonical reports.
- UNCHANGED cannot carry a replacement project/history; read-only output must
  match the operation's contract. COMPATIBILITY must match the current ledger.

All candidate values/reports remain local until validation completes. Both the
pre- and post-validation epoch/snapshot guards remain, as do cancellation and
single-writer. Invalid direct accept throws without modifying canonical/session
fields. Normal run/poll catches the error and finishes the failed operation while
retaining the original project. No APPEND silently degrades to REPLACE. Save
publication remains after successful protocol validation and file-stamp checks.
