## 1. Root cause

RF-02 proved that a response had a valid policy, canonical project and exact
value-to-delta record pairing. It did not prove that these records were produced
for the pending operation. Another genuine Packaging BUMP result could satisfy
a pending NOMINAL request; a real BUMP-engine result could be relabelled at the
outer envelope. Correct internal physics is necessary but not sufficient.

## 2. Authority and correspondence

`Controller.Operation` is the immutable owner request. Its original project,
arguments and action, not a returned action/fingerprint, determine the expected
configuration transition and physical scenario. `workerRequest(Operation)`
reproduces the same reduced input contract used at dispatch, without dropping
the owner's canonical ledger.

`perform` and `validateOperationResponse` share the private `operationBody`.
Execution calls the existing public engines. Verification reconstructs only
declarations/configuration, substitutes already canonically validated records
at each engine boundary, and checks their requested result ID, actual engine,
complete scenarioAtExecution and original projectAtExecution snapshot.
No forward solve or fresh optimization runs during receipt. Canonical historical
search validators may replay their controller against stored records, as before.
Native validation may still recompute algebraic/clearance checks or analyze stored
poses; this is real validation cost, not newly generated motion/search evidence.

Canonical validation first reconstructs `prepared` from that execution snapshot
and scenario; verifies identity, revision and provenance; and checks the actual
native payload against its geometry, definition, plan, parent and options. The
new owner-to-snapshot/scenario binding therefore constrains the **actual native
content**, not just a second worker-supplied label. The reconstructed final delta
also rejects unrelated configuration/resource changes and extra/missing results.

Equality here applies to deterministic declarations/configuration or to the same
validated stored records, NOT to two independently executed numerical results.
No elapsed time is recomputed and compared to a fresh solve. char/string result
IDs normalize only comparison keys; original IDs, identities, snapshots and MAT
representations remain untouched. Expected IDs are exact, not prefixes/case folds.
Canonical factories retain their existing SI/unit/shape/solver-option rules.

## 3. Minimal metadata extension

- `REFERENCE_TARGETS` alone returns `referenceSweep` in addition to the eight RF-02
  fields. Its existing explicit software-reference BUMP executes once. Receipt
  validates this complete native sweep, its expected reference geometry/grid and
  stored poses, then derives the same existing targets using native analysis.
  It cannot simply trust returned target values or start another BUMP. No new
  physical inputs, target advice, tolerances or equations are introduced. This is
  transient response evidence, not a new persisted project format.
- LOAD records the requested local file stamp as `Operation.arguments.sourceStamp`.
  Receipt rejects a changed source and canonically reloads the **requested** MAT
  to verify returned content, including legitimate full-history replacements.
- SAVE receipt canonically reads its operation-owned temporary MAT and checks its
  complete logical project against the requested project before publication.
  It does not write a second file. The existing destination-stamp, overwrite and
  final atomic move remain in place.

Local MATs remain trusted inputs. Stamp/content checks and a single-session writer
are not an adversarial filesystem lock; an external writer between check and
move/read remains outside this contract. No distributed/security guarantee.
MAT regressions use absolute file paths and a stable working folder/path; they
do not certify arbitrary external filesystem or MATLAB path mutation mid-task.

## 4. Receipt order and atomicity

1. Pending Busy/Operation must exist; validate the closed envelope (extra reference
   sweep only for its action), operation ID/action/epoch and owner-derived policy.
2. Existing stale/cancel gates discard obsolete work without applying it.
3. Validate value/delta pairing and the complete canonical project/native evidence.
4. Verify its semantic correspondence against the owner operation, locally.
5. APPEND uses the existing canonical history merger and compatibility calculation;
   REPLACE validates and matches the complete requested replacement; UNCHANGED
   cannot carry a replacement project/history.
6. Recheck owner snapshot/epoch and cancellation after validation, then commit
   project/session state, or publish the exact owned SAVE temporary MAT.

No semantic rejection mutates Project, ledger, compatibility, epoch, file, dirty
flag, last output/action/timing/error, operation or transport state. Existing poll/
run error handling may subsequently record the failure and finish the operation.
Single-writer, completion reentry guard, cancellation and selective STALE remain.

## 5. Systematic operation matrix

Policy A=APPEND, R=REPLACE, U=UNCHANGED. All bindings use the owner request.
Negative cases in `TestGuidedOperationSemantics` use genuine canonical alternative
projects/results unless a malformed envelope/policy is explicitly being tested
by `TestGuidedResponseProtocol`.

## 7. Scope and limits

Only operation receipt/routing, its tests and documentation change. The existing
perform switch moves into a shared private implementation to keep execution and
verification declarations from drifting; it is not an engineering refactor.
No files under `src/+fsd` are intentionally changed by RF-03. Mathematical
algorithms, geometric conventions, physical tolerances, synthesis controllers,
scores and historical native evidence remain unchanged.

Canonical validation/reconstruction and additional MAT verification can block
owner callbacks and take time. This work does not optimize that cost or promise
continuous UI responsiveness, small-job parallel speedup, unlimited history/RAM
capacity, continuous collision clearance, CAD/manufacturing or regulatory approval.
Retain the accepted performance/UX limitations from the preceding validation.
The read-only UI observer logs changed states, not a periodic heartbeat; gaps
between its entries do not measure callback latency. Navigation checks at actual
EXECUTING/DECODING transitions do not certify uninterrupted responsiveness.
Independent RF-03 and complete reception-contract reaudit is still required.
